# SupportSense

**A SwiftUI app that takes a support question and returns ranked answer cards from a local knowledge base, each with a one-line summary, a confidence label, and thumbs-up/down feedback capture.** Everything runs on the device: no network, no API bill, nothing the user types leaves the phone.

> **The headline result is a warning, not a win.** On questions I wrote while looking at the articles, top-1 accuracy is **98.4%**. On a frozen held-out set written the way real users talk, it is **23.1%**. The confidence labels survived that drop: across both sets, **zero wrong answers were labelled High**. So the app knows when it doesn't know, and says so. See [POSTMORTEM.md](POSTMORTEM.md).

---

## The problem

A user types "I was charged twice" into a help screen. They need the right article **first**, and an honest signal when the app isn't sure, so they rephrase or reach a human instead of following the wrong instructions. Support teams also need to know which answers helped, so the library can improve.

Think of a good pharmacist. Sometimes they hand you the answer. Sometimes they say "it's probably this, but check with your GP." The useless pharmacist is the one who always sounds certain.

## What it does

| Requirement | How |
|---|---|
| Accept a support question | `.searchable` field, plus suggestion chips on the empty screen |
| Ranked answer cards | BM25 over title (×2), tags (×2) and body; top 5 cards |
| Summaries | Extractive: the article sentence that shares the most words with the question. It cannot hallucinate, because it only quotes. |
| Confidence labels | High / Medium / Low from query coverage, score, and lead over #2. Only the top card can be High. Colour, text and icon shape all change (accessibility). |
| Feedback capture | Thumbs up/down per card, persisted to JSON by an actor; viewable and exportable in a Feedback log sheet. Votes nudge future rankings by at most ±15%. |
| Low-confidence honesty | If the best card is Low, a banner tells the user to rephrase or contact support. |

## Architecture

```mermaid
flowchart LR
    U[User question] --> V[ContentView<br/>SwiftUI]
    V --> VM[SearchViewModel<br/>@Observable, @MainActor]
    VM --> E[SearchEngine<br/>value type]
    subgraph Core["SupportSenseCore (Swift package, tested on macOS + Linux)"]
        E --> N[Normalizer<br/>split → phrases → synonyms → stopwords → stem]
        E --> I[BM25Index]
        E --> S[Summarizer<br/>extractive]
        E --> C[Confidence rules]
        L[(lexicon.json<br/>all thresholds)] --> N
        L --> C
        K[(knowledge_base.json<br/>30 articles)] --> I
    end
    VM <--> F[JSONFileFeedbackStore<br/>actor]
    F --> D[(feedback.json<br/>Application Support)]
    F -. net votes ±15% .-> E

    P[tools/reference_ranker.py<br/>Python mirror] --> G[(eval/golden.json)]
    L --> P
    K --> P
    G --> T[EvalTests: Swift must match Python<br/>to 1e-9 on every query]
```

The engine is a plain Swift package with no UI imports, so `swift test` runs on Linux CI with no simulator. The Python mirror reads the **same** `lexicon.json` and knowledge base, produces the eval numbers, and writes `golden.json`. A Swift test then fails if Swift ranks or scores a single query differently. The README numbers are therefore checked on two runtimes.

## Eval results

Generated by `make eval` (`eval/RESULTS.md`). Dev = 63 in-scope + 7 out-of-scope questions. Held-out = 26 + 4, written in slang and indirect phrasing, frozen, never tuned against.

| Metric | Dev set (63+7 OOS) | Held-out set (26+4 OOS) |
|---|---|---|
| Top-1 accuracy | 98.4% | 23.1% |
| Hit@3 | 98.4% | 38.5% |
| MRR | 0.984 | 0.320 |
| Precision when labelled **High** | 100.0% (40/40) | n/a (0/0) |
| In-scope queries labelled High | 63.5% | 0.0% |
| Out-of-scope wrongly labelled High | 0.0% | 0.0% |

| Shared metric | Value |
|---|---|
| Attack success rate (12 adversarial inputs) | 0.0% |
| Cost per task | $0.00 (on-device, no API calls) |
| Latency p50 / p95 (Python reference, 3000 runs) | 0.024 ms / 0.047 ms |

| Top-card confidence (held-out) | Count | Correct | Accuracy |
|---|---|---|---|
| High | 0 | 0 | n/a |
| Medium | 11 | 5 | 45.5% |
| Low | 13 | 1 | 7.7% |

**How to read this.** Confidence is well calibrated: High was right 40/40 times, Medium 26/32 across both sets, Low 2/15. The weakness is recall on unfamiliar vocabulary, which is what the next step targets.

**Attack success rate** counts an attack as successful if it produced any High-confidence card, crashed, took over 250 ms, or (for keyword stuffing) changed the ranking vs. the clean query. The 12 inputs cover keyword stuffing, prompt-injection text, SQL syntax, empty/whitespace/emoji-only, a 20,000-character query, stopword-only, and mixed intents. There is no LLM in the loop, so injection text is just words; it is tested to prove that.

**Latency.** The table shows the Python reference. The Swift engine prints its own p50/p95 in CI (`SUPPORTSENSE_LATENCY` line in the `swift test` log) and fails if p95 exceeds 5 ms.

## Known failures

| Query (held-out) | What happened | Why |
|---|---|---|
| "binned a folder by mistake" | Ranked *Share a folder* first | "binned" ≠ "deleted"/"trash" — vocabulary mismatch |
| "says I've run out of room" | No storage article in top 3 | "room" ≠ "storage"/"space" |
| "speak to someone real" | No results | none of the words appear in the KB |
| "how much is 2TB" | No results | KB writes "2 TB"; tokeniser keeps "2tb" as one token |
| "passwrd reset" | Right answer, Medium only | no typo tolerance; "reset" alone carried it |
| "charged twice this month" | *Refund* ranked above *Unrecognised charge* | both match "charge"; no notion of "twice" |
| Feedback boost | Global per-article, not per-question | popular articles could be pushed for unrelated queries |

Full list: `eval/results.json → sets.holdout.failures`.

## Next steps

1. **Semantic re-ranker.** Re-rank BM25's top 10 with on-device sentence embeddings (`NLEmbedding`). Target: held-out top-1 ≥ 60% with still zero wrong High labels. This fixes most of the table above.
2. **Typo tolerance:** edit distance ≤ 1 against the KB vocabulary for unmatched terms.
3. **Number/unit tokenising:** "2TB" → "2 tb".
4. **Per-question feedback** keyed on (normalised query, article) to remove popularity bias.
5. **Bigger held-out set** from real tickets. n = 26 gives roughly ±16 percentage points of uncertainty at 95%.

`scripts/seed_project_board.sh` adds these to the [Projects board](https://github.com/users/paulmadojutimi94/projects/1).

## Run it

```bash
make test        # swift test: unit, parity, quality gates, latency (macOS or Linux)
make eval        # Python 3 stdlib only; regenerates eval/*.json and RESULTS.md
brew install xcodegen
make open        # generates App/SupportSense.xcodeproj and opens it → Run on an iOS 17 simulator
```
